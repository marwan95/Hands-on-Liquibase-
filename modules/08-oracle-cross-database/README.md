# Module 08 – Oracle & cross-database changelogs

**Goal:** deploy the same changelog to PostgreSQL **and** Oracle.
**Time:** ~60–90 min

---

## 1. Concepts

### Same changelog, different settings file
```bash
liquibase --defaults-file=liquibase-oracle.properties status --verbose
```
Docker users: `docker compose run --rm liquibase-oracle status --verbose`

The local Liquibase install has only the PostgreSQL driver. For Oracle, run this once in `lab/`:
```bash
lpm add oracle-ojdbc11      # installs into lab/liquibase_libs/, which is loaded automatically
```
(The Docker CLI image already includes both drivers.)

### The `dbms` attribute
```sql
--changeset yourname:1 dbms:postgresql
CREATE TABLE customers (customer_id SERIAL PRIMARY KEY, ...);

--changeset yourname:1-ora dbms:oracle
CREATE TABLE customers (customer_id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, ...);
```
- Each database runs only its own version. A changeset for the other database is **filtered out silently** ("DBMS mismatch") and never shows as pending.
- Values: `postgresql`, `oracle`, `mssql`, `mysql`, `h2`... Combine them (`dbms:postgresql,h2`) or exclude one (`dbms:!oracle`). In YAML: `dbms: oracle`.
- Adding `dbms:` to the header of a deployed changeset does **not** change its checksum.

**The professional strategy:**
1. Prefer YAML/XML change types: they're portable for free.
2. Leave SQL that is valid on both databases alone.
3. Use `dbms` twins only for truly database-specific SQL. Put each `-ora` twin **right after** its PostgreSQL version so the order stays correct.

### PostgreSQL → Oracle cheat sheet
| PostgreSQL | Oracle |
|---|---|
| `SERIAL PRIMARY KEY` | `NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `VARCHAR(n)` / `NUMERIC(p,s)` / `INT` | `VARCHAR2(n)` / `NUMBER(p,s)` / `NUMBER` |
| `ALTER TABLE t ADD COLUMN c ...` | `ALTER TABLE t ADD c ...` |
| `ALTER TABLE t ALTER COLUMN c TYPE ...` | `ALTER TABLE t MODIFY c ...` |
| `now()` / `TEXT` | `SYSTIMESTAMP` / `VARCHAR2(4000)` or `CLOB` |
| `pg_indexes WHERE indexname = 'x'` | `user_indexes WHERE index_name = 'X'` (UPPERCASE) |
| PL/pgSQL `$$ ... $$` | PL/SQL `IS ... BEGIN ... END;` and a `/` line → `splitStatements:false endDelimiter:/` |

## 2. Hands-on

**Step 1: Prepare Oracle.**
- Make sure `docker compose ps` shows `hol-oracle` as **healthy**.
- Add these to `lab/liquibase-oracle.properties`:
  ```properties
  parameter.schema=LB_LAB
  context-filter=prod
  ```
- Local install only: run `lpm add oracle-ojdbc11` in `lab/`.

**Step 2: See the failure first (dry run only):**
```bash
liquibase --defaults-file=liquibase-oracle.properties update-sql > oracle-preview.sql
```
Compare what Liquibase generated for `suppliers` (YAML) with your `customers` (raw SQL). Which one is valid Oracle?

**Step 3: Tag the PostgreSQL-only changesets.** Add `dbms:postgresql` to the header (keep the other attributes):
- `module01.sql`: 1, 2, 3, 4, 5
- `module03_routines.sql`: m3-fn-1
- `module05.sql`: m5-1
- `module06.sql`: m6-1
- `module07.sql`: m7-1, m7-3

**Step 4: Write the Oracle twins** (`dbms:oracle`), each right after its PostgreSQL version:
- `module01.sql`: `1-ora` to `5-ora`, with Oracle rollbacks
- `module05.sql`: `m5-1-ora`
- `module06.sql`: `m6-1-ora` (`user_indexes`, uppercase index name)
- `module07.sql`: `m7-1-ora`, `m7-3-ora` (keep `${schema}`)
- `module03_routines.sql`: this one is given, since PL/SQL may be new to you:
  ```sql
  --changeset yourname:m3-fn-1-ora dbms:oracle splitStatements:false runOnChange:true endDelimiter:/
  CREATE OR REPLACE FUNCTION fn_customer_total(p_customer_id IN NUMBER)
  RETURN NUMBER
  IS
      v_total NUMBER;
  BEGIN
      SELECT ROUND(NVL(SUM(amount), 0), 2) INTO v_total
      FROM orders
      WHERE customer_id = p_customer_id;
      RETURN v_total;
  END;
  /
  --rollback DROP FUNCTION fn_customer_total;
  ```

**Step 5: Prove PostgreSQL is unaffected:**
```bash
liquibase validate
liquibase status --verbose      # nothing new should be pending except runAlways m5-2
```

**Step 6: Deploy to Oracle:**
```bash
liquibase --defaults-file=liquibase-oracle.properties update
```
You **will** hit at least one Oracle error that has nothing to do with syntax. Read it carefully and fix it.
<details><summary>Hint: if you get ORA-01408</summary>

`ORA-01408: such column list already indexed` on `CREATE INDEX idx_customers_email`: `email` is `UNIQUE`, and Oracle automatically indexes unique columns and refuses a second index on the same column. PostgreSQL allows it. Make `m5-3` PostgreSQL-only. **Don't** add a comment line inside it: that would change its checksum on PostgreSQL!
</details>

When an update fails halfway, the successful changesets are already recorded. Fix the problem and run `update` again; it continues where it stopped.

**Step 7:** Check Oracle (CloudBeaver: host `oracle`, port 1521, service `FREEPDB1`, user/password `lb_lab`):
```sql
SELECT object_type, object_name, status FROM user_objects ORDER BY 1, 2;
SELECT fn_customer_total(1) FROM dual;
```
