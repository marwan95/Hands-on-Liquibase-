# Module 02 – Solutions

## Hands-on
- **YAML:** [module02.yaml](lab/changelog/module02.yaml). In `update-sql`, `INT` + `autoIncrement: true` becomes an auto-increment column on PostgreSQL (`INTEGER GENERATED BY DEFAULT AS IDENTITY`) and an identity column on Oracle. Same file, the right SQL for each database.
- **XML:** [module02.xml](lab/changelog/module02.xml). Watch the spec: `city` is **VARCHAR(80)**; the grader checks it.
- **Widening `full_name`:**
  ```sql
  --changeset yourname:5
  ALTER TABLE customers ALTER COLUMN full_name TYPE VARCHAR(200);
  --rollback ALTER TABLE customers ALTER COLUMN full_name TYPE VARCHAR(100);
  ```
  The rollback restores the **previous** value (100), not the new one. A common mistake is a rollback that repeats the change, or targets the wrong table or column.
- **Master** (order matters):
  ```yaml
  databaseChangeLog:
    - include: { file: module01.sql, relativeToChangelogFile: true }
    - include: { file: module02.yaml, relativeToChangelogFile: true }
    - include: { file: module02.xml, relativeToChangelogFile: true }
  ```
  Pick **one** include style (`relativeToChangelogFile: true`) and keep it for the whole project. Switching later changes the stored paths, and with them the changeset identities.

## Quiz
| Q | Answer | Why |
|---|---|---|
| q1 | **C** | Alphabetical: "1" < "2", so `10_indexes` sorts before `2_tables`. Zero-pad your file names. |
| q2 | **A** | Change types carry their meaning, so Liquibase knows the inverse (`createTable` → `DROP TABLE`). Raw SQL is just text to Liquibase. |
| q3 | **D** | The new path makes them "new" changesets → `CREATE TABLE customers` again → "relation already exists". |
| q4 | **B** | `logicalFilePath` fixes the identity no matter where the file lives. |
| q5 | **C** | Database-independent SQL + automatic rollback. (Stored procedures are actually a reason to use **SQL**.) |
